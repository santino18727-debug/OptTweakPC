Synthèse

L'application était un prototype issu du template Tauri (1 écran, 4 boutons, 4 commandes Rust wrappant du PowerShell) avec un bug visuel actif, aucune confirmation avant action système, et des listes de services codées en dur spécifiques à la machine de dev. Après le pipeline, c'est une app avec garde-fous de sécurité, contrat d'API typé, aperçu avant action (dry-run), annulation (undo), contexte système et accessibilité de base.

✅ Patterns gagnants adoptés

  • Description + indicateur de risque par action (ShutUp10++, WinUtil)
  • Aperçu (dry-run) avant d'agir (inspiré du « voir ce qui change »)
  • Undo via snapshot d'état (WinUtil, ShutUp10++)
  • Contexte hardware à l'accueil (Wintoys)

⛔ Anti-patterns évités

  • Tweaks « magiques » sans explication
  • Registry cleaner placebo (CCleaner)
  • Faux boosters FPS/RAM non vérifiables
  • Monétisation agressive / dark patterns
  • Tweaks irréversibles sans avertissement

Sources : oo-software.com · binaryfork.com (Wintoys) · christitus.com (WinUtil) · github.com/hellzerg/optimizer · cybernews.com & time.com (CCleaner) · betanews.com (BleachBit) · remote.tools (Razer Cortex).

4.Décision du conseil (4 perspectives)

Le conseil a fait débattre les angles pragmatique, puriste/architecte, sécurité et performance/UX, puis tranché.

Écartés comme sur-ingénierie pour une app de cette taille (YAGNI) :
  • Mode Safe/Avancé + export/import profil JSON — aucun usage multi-machine aujourd'hui. À re-débattre si distribution.
  • Dashboard hardware complet — dégradé à 4 valeurs read-only (gardé), pas un dashboard.
  • Journal persistant sur disque — dégradé à un journal de session en mémoire (gardé).
Piège technique central (ordonnancement) : le contrat invoke<string> + le routage d'erreur par startsWith("Erreur") ne devaient changer qu'une seule fois, proprement, en itération 2 — jamais en mélangeant typage et cosmétique. Tout le reste a été ordonné autour de cette contrainte.

5.Application — 3 itérations

IT. 1

Sécurité de base + le proto cesse d'être cassé

100 % additif — aucune signature Rust modifiée, le front reste sur invoke<string>.

  • Bug CSS corrigé : styles .status-box / .success / .error + résidus template supprimés
  • Boutons : :disabled, :focus-visible, CTA primaire, bouton « Nettoyer » en warning
  • Badges de risque + descriptions enrichies par action ; aria-live / role=status
  • Modale de confirmation avant action destructive (sans dépendance — modale React native)
  • Reset du statut + loading par-commande (state activeCommand)
  • Rust : chemin absolu powershell.exe ; nouvelle commande check_admin_rights + bannière d'avertissement

src/App.tsx · src/App.css · src-tauri/src/core/system.rs (nouveau) · backup.rs · performance.rs · startup.rs · lib.rs

IT. 2

Bascule vers le contrat typé (mouvement coordonné)

La seule itération qui change le contrat front↔back — faite d'un bloc, commande par commande.

  • audit_startup → Vec<StartupEntry> rendu en table propre (fini le dump texte)
  • clean_startup → CleanupResult typé ; nouvelle commande preview_startup_cleanup (dry-run)
  • Dry-run et application partagent exactement la même liste de cibles → l'aperçu ne peut pas mentir
  • Détection dynamique : les services absents sont rapportés, plus d'erreur — l'app devient portable
  • Liste élargie aux updaters courants (Google/Edge/Brave) ; chromoting toujours exclu
  • Canal d'erreur unifié : suppression du startsWith("Erreur"), erreurs via try/catch

src/App.tsx · src/App.css · src-tauri/src/modules/startup.rs · lib.rs

IT. 3

Réversibilité + contexte (versions minimales)

Additif au-dessus du contrat typé.

  • Undo : clean_startup sauvegarde un snapshot d'état (%LOCALAPPDATA%\OptTweakPC) ; restore_startup restaure le type de démarrage d'origine
  • Bouton « ↩ Annuler le nettoyage » visible seulement si un snapshot existe (has_startup_snapshot)
  • Avant/après : colonne « Avant » dans les tables (état précédent capturé)
  • Contexte système : get_system_info → plan d'alim, RAM libre, nb programmes au démarrage, CPU
  • Journal de session horodaté (en mémoire, 20 dernières actions)

7.Reste à faire / recommandations

  • Test runtime en admin — lancer l'app, vérifier chaque commande de bout en bout (notamment le throttling Windows du point de restauration < 24 h, signalé à l'audit).
  • Implémenter réellement optimize_performance ou le marquer « bêta » — actuellement il n'active que le plan d'alimentation.
  • Vérifier le GUID du plan d'alim avant application (peut ne pas exister sur certaines configs OEM).
  • Manifeste d'élévation Windows — décision séparée (change le comportement de lancement, potentiellement cassant au packaging) ; non traité ici volontairement.
  • Audit sécurité dédié — une app qui touche services/registre en admin mérite une passe security-reviewer avant toute distribution.
  • Réactivés différés (it.1) — mode Safe/Avancé et export de profil : à reconsidérer si l'app est distribuée à d'autres postes.
